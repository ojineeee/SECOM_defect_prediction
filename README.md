# SECOM 반도체 공정 불량 예측 프로젝트

**프로젝트 요약**: 590개 공정 센서로 웨이퍼 불량 가능성을 예측하고, 고차원·불균형 제조 데이터에서 **평가 방식과 시간 드리프트가 성능 해석을 어떻게 바꾸는지** 검증한 개인 프로젝트입니다.

- 데이터 출처: [UCI SECOM Data Set](https://archive.ics.uci.edu/dataset/179/secom) (공개 데이터, Kaggle에도 동일하게 게재됨)
- 사용 기술: Python, pandas, scikit-learn, XGBoost
- 전체 코드/결과: 전처리부터 평가·시각화까지 재현할 수 있습니다 ([실행 방법](#부록-직접-실행해보고-싶다면))

| 구분 | 포트폴리오 핵심 내용 |
|---|---|
| 문제 | 불량률 6.6%인 센서 데이터에서 최종 검사 전 불량 후보 선별 |
| 접근 | 누수 방지 Pipeline, SMOTE, 4개 분류 모델, One-class 비교, SHAP |
| 검증 | 무작위 분할과 시간순·Walk-forward 평가를 분리하고 95% 신뢰구간 제시 |
| 주요 결과 | 무작위 test Recall 0.381·PR-AUC 0.152, 시간순 test Recall 0.000·PR-AUC 0.084 |
| 핵심 판단 | 현재 성능은 자동 판정용이 아니라 재검사 우선순위화 가능성을 탐색한 수준이며, 배포 전 드리프트 대응이 필요 |

## 이 프로젝트가 푸는 문제

반도체 공정에서는 웨이퍼 하나가 만들어지는 동안 수백 개의 센서가 온도, 압력, 시간 같은 값을 계속 기록합니다. 이 센서 기록만 보고, **최종 검사를 하기 전에 "이 웨이퍼는 불량일 가능성이 높다"를 미리 알아낼 수 있는지**를 확인하는 것이 이 프로젝트의 목표입니다.

이게 가능해지면 실제 공정에서는:
- 불량 가능성이 높은 웨이퍼를 더 꼼꼼히 재검사하거나
- 문제가 되는 센서/공정 구간을 먼저 점검하는 식으로

**불량을 사후에 발견하는 대신 사전에 걸러내는 데 도움을 줄 수 있습니다.**

---

## 전체 진행 순서

```
1단계. 데이터를 뜯어본다 (EDA)         →  데이터의 특징과 함정을 파악
2단계. 머신러닝 모델을 만든다           →  실제로 예측이 가능한지 검증
3단계. 모델이 왜 그렇게 판단했는지 설명한다 (SHAP)  →  블랙박스를 열어서 확인
4단계. 운영 환경을 가정해 재검증한다 (시간순 분할)      →  과거로 학습해 미래 구간을 평가
5단계. 결과를 정직하게 해석한다         →  잘 된 점과 한계를 함께 정리
```

## 1단계. 왜 모델부터 만들지 않고 데이터를 먼저 뜯어봤는가 (EDA)

집을 짓기 전에 땅부터 파봐야 하듯, 데이터로 뭔가를 예측하기 전에는 **이 데이터를 믿어도 되는지, 어떤 함정이 있는지**를 먼저 확인해야 합니다. 이 단계를 EDA(탐색적 데이터 분석)라고 부릅니다. 확인 없이 바로 모델부터 돌리면, 데이터의 결함을 모델의 성능 문제로 착각하기 쉽습니다.

### 확인한 것들과 발견한 사실

**① 불량이 너무 적습니다.** 전체 1,567개 웨이퍼 중 불량은 104개(6.6%)뿐입니다. 이 사실을 놓치면 "정확도 93%"라는 숫자에 속기 쉽습니다 — 사실은 전부 "정상"이라고 찍기만 해도 나오는 숫자이기 때문입니다. 그래서 이 프로젝트에서는 정확도 대신 **실제 불량 중 몇 개를 찾아냈는가**를 기준으로 삼았습니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/01_label_distribution.png" width="380" alt="정상/불량 분포">

**② 결측치가 무작위가 아니라 뭉쳐서 나타납니다.** 센서값이 비어있는 컬럼 24개를 살펴보니, 무작위로 흩어져 있는 게 아니라 `109·110·111번`, `382·383·384번`처럼 **연속된 센서 번호끼리 뭉쳐서** 비어 있었습니다. 이는 개별 센서 고장이 아니라 **특정 계측 장비(다채널 센서 모듈) 하나가 특정 시점에 데이터를 못 남겼을 가능성**을 시사합니다. 실제 현업이라면 "이 장비군을 점검해보라"고 제안할 수 있는 단서입니다.

**③ 시간이 지날수록 불량률이 떨어지는 추세가 있었습니다.** 데이터가 수집된 3개월(2008년 7월~10월) 동안의 불량률을 시간 순으로 나눠보니, 앞 절반은 8.6%, 뒤 절반은 4.7%로 눈에 띄게 줄어들었습니다. 이 데이터만으로는 원인(공정 개선인지, 조업 조건 변화인지, 다른 요인인지)까지는 알 수 없지만, **시간이라는 변수 자체가 불량 여부와 관련된 신호를 담고 있다**는 것은 분명해 보였습니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/02b_defect_rate_drift.png" width="560" alt="시간에 따른 불량률 변화">

**④ "중요해 보이는" 센서들끼리도 사실 같은 정보를 담고 있었습니다.** 불량 예측에 도움이 될 만한 센서 상위 10개를 뽑아봤더니, 그중 일부는 서로 96%까지 거의 동일하게 움직이는 것으로 나타났습니다. 즉 "정보력 있는 센서 10개"처럼 보여도 실제로는 겹치는 정보가 많다는 뜻이며, 이는 데이터 전체가 겉보기보다 단순한 구조를 가지고 있을 수 있다는 근거이기도 합니다.

### EDA에서 실제 모델링으로 이어진 것

③에서 발견한 "시간이 지날수록 불량이 준다"는 사실을 그냥 관찰로 끝내지 않고, **"학습 데이터의 시작일로부터 며칠이 지났는가"라는 파생변수**를 만들어 모델에 추가했습니다. 기준일은 train에서만 정하고 validation/test에도 동일하게 적용해 시간축의 의미가 바뀌지 않도록 했습니다. 이 변수는 교차검증에서 Recall 개선이 관측되어 최종 피처에 포함했습니다.

## 2단계. 어떤 머신러닝 기법을 썼고, 왜 그런 결과가 나왔는가

이 프로젝트는 두 가지 방식을 각각 시도하고 비교했습니다.

| 방식 | 하는 일 | 이 프로젝트에서의 이름 |
|---|---|---|
| **지도학습 (분류)** | "정상/불량" 정답을 이미 아는 과거 데이터로 학습해서, 새 웨이퍼가 나오면 정상인지 불량인지 예측 | 양불 판정 |
| **One-class 이상탐지** | 정상 패턴을 학습해 여기서 벗어나는 샘플을 탐지. 단, 피처 선택에는 라벨 사용 | 이상 탐지 |

### 왜 두 가지를 다 해봤는가
현업에서는 항상 불량 라벨이 충분한 것은 아닙니다. 라벨을 직접 학습하는 분류 모델과 정상 분포를 중심으로 학습하는 One-class 모델을 비교해, **라벨 활용 방식에 따라 탐지력이 어떻게 달라지는지** 확인했습니다.

### 지도학습 (양불 판정) — 어떻게 진행했는가

1. **불균형 문제 먼저 해결**: 불량이 6.6%뿐이라 아무 조치 없이 학습하면 모델이 "그냥 다 정상"이라고 찍어버립니다. 이를 보정하는 방법 3가지(SMOTE 등)를 비교해서 가장 나은 방법을 선택했습니다.
2. **모델 4종 비교**: Logistic Regression(단순한 통계 모델), Random Forest, XGBoost, SVM 4가지를 동일한 조건에서 비교했습니다.
3. **최종 모델 검증**: 학습에 전혀 쓰지 않은 데이터(전체의 20%)로 진짜 성능을 확인했습니다.

**결과**: 의외로 가장 단순한 모델인 **Logistic Regression**이 가장 좋은 성능을 보였습니다. 복잡한 모델(Random Forest, XGBoost)이 오히려 더 낮은 성능을 보였는데, 이는 데이터 양(1,567개)에 비해 변수(590개)가 너무 많아 복잡한 모델이 데이터를 "외워버리는" 과적합 현상 때문으로 해석됩니다. **복잡한 모델이 항상 좋은 건 아니다**라는, 데이터 규모를 고려해야 한다는 인사이트를 확인한 부분입니다.

최종적으로 실제 불량 21건 중 **8건을 사전에 찾아냈습니다** (Recall 0.381). 다만 이 지점은 Precision이 0.098에 불과해, 8건을 잡기 위해 **정상 웨이퍼도 약 74건을 함께 "불량 의심"으로 잘못 지목**했다는 뜻이기도 합니다 — 재검사 비용을 감안하면 이 트레이드오프도 같이 봐야 하는 숫자입니다. 임계값을 조절하면 이 균형을 바꿀 수 있고, 그 구체적인 수치는 [4-5. 운영 관점에서 다시 보기](#4-5-운영-관점에서-다시-보기-recall상위-n-오경보-빈도-precision고정-recall)에서 다룹니다.

### One-class 기반 이상 탐지 — 어떻게 진행했는가

정상 데이터만 모델에 보여주고 "정상 패턴"을 학습시킨 뒤, 여기서 벗어나는 웨이퍼를 이상치(=불량 후보)로 판단하는 두 가지 기법(Isolation Forest, One-Class SVM)을 시도했습니다. 완전한 비지도 학습은 아닙니다 — 피처 선택 단계(60개 센서 추림)는 라벨을 쓰는 mutual information 기준으로 이루어지므로 약한 지도 신호가 섞여 있고, contamination/nu 값도 실제 불량률을 모른다고 가정하고 일반적으로 쓰이는 보수적 기본값(5%)을 사용했습니다.

**공정 비교가 먼저 필요했습니다**: One-class 모델은 contamination=5%로, 지도학습은 기본 threshold(0.5)로 그냥 비교하면 두 방식이 실제로 "몇 장을 의심 대상으로 지목하는가"부터 달라져 Recall을 그대로 비교하는 게 불공정합니다. 그래서 **세 모델 모두 테스트셋(314장)에서 가장 의심스러운 상위 5%(16장)를 플래깅했을 때**를 기준으로 다시 비교했습니다.

| 방법 | 검출 불량 | 상위 5% 플래깅 시 Recall | Precision |
|---|---:|---:|---:|
| 지도학습 (Logistic Regression) | **3/21건** | **0.143** | **0.188** |
| One-Class SVM | 1/21건 | 0.048 | 0.062 |
| Isolation Forest | 0/21건 | 0.000 | 0.000 |

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/10_anomaly_vs_supervised.png" width="480" alt="One-class 이상탐지 vs 지도학습 비교 (동일 경고 예산)">

같은 예산(16장)에서도 지도학습이 가장 많이 잡아냈습니다. (참고: 각 모델의 기본 설정 그대로 썼을 때는 One-class 두 모델 모두 Recall 0.048, 지도학습은 threshold 0.5에서 Recall 0.381이었는데, 이건 서로 다른 개수를 플래깅한 상태에서 나온 숫자라 직접 비교에는 위 표를 기준으로 삼아야 합니다.)

**인사이트**: 이 split의 동일 경고 예산에서는 지도학습이 One-Class SVM보다 더 많은 불량을 검출했습니다(3건 vs 1건). 다만 불량 표본이 21건뿐이므로 일반적인 우열로 단정하지 않고, **이 데이터에서는 라벨을 활용한 분류 모델을 우선 후보로 두되 추가 데이터에서 재검증해야 한다**고 해석했습니다.

## 3단계. 모델이 왜 그렇게 판단했는지 설명하기 (SHAP)

지금까지는 "모델이 얼마나 잘 맞히는가"만 봤습니다. 그런데 실제 현업에서는 성능만큼이나 **왜 이렇게 판단했는가**도 중요합니다 — 담당자가 그 이유를 납득해야 실제로 재검사나 공정 점검 같은 조치로 이어질 수 있기 때문입니다. 이걸 확인하는 대표적인 방법이 **SHAP**입니다.

이전에 본 "계수 크기(|coefficient|)" 순위는 모델 전체를 기준으로 한 평균적인 영향력이었습니다. SHAP은 여기서 한 걸음 더 나아가 (1) 센서들 사이의 상관관계까지 반영하고, (2) **개별 웨이퍼 한 장 단위로** "이 센서가 불량 판정에 이만큼 기여했다"를 숫자로 분해해서 보여줍니다.

### 계수 순위 vs SHAP 순위 — 절반 이상이 달랐습니다

상위 15개 중요 피처를 계수 기준과 SHAP 기준으로 각각 뽑아 비교했더니, **겹치는 피처는 15개 중 5개뿐**이었습니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/11_shap_importance_bar.png" width="560" alt="SHAP 기준 상위 15개 피처 중요도">

가장 눈에 띄는 차이는 **`days_since_start`(1단계에서 만든 시간 파생변수)의 순위가 크게 뛴 것**입니다. 계수 크기만으로는 상위 15위 밖이었지만, 상관구조를 반영한 SHAP 설정에서는 **3위**였습니다. 이는 중요도 순위가 해석 방법에 따라 달라질 수 있으며, 시간 변수가 모델 판단에 적지 않게 사용됐다는 것을 보여줍니다. 동시에 공정 원인 변수가 아니라 수집 시점을 학습한 **shortcut 신호일 가능성**도 있어, 시간순 검증과 함께 해석했습니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/12_shap_beeswarm.png" width="640" alt="SHAP beeswarm summary plot">

위 그래프는 각 센서 값이 높을 때(빨강)/낮을 때(파랑) 예측에 어느 방향으로 영향을 주는지까지 보여줍니다 — "이 센서 값이 크면 불량 쪽으로 밀어붙인다" 같은 해석이 가능해집니다.

### 개별 사례로 확인하기

실제로 불량이었고 모델도 불량(97.6% 확률)으로 정확히 맞힌 웨이퍼 하나를 골라, "왜 이렇게 판단했는가"를 분해해봤습니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/13_shap_individual_example.png" width="640" alt="개별 웨이퍼에 대한 SHAP 설명">

이렇게 특정 웨이퍼 단위로 "어떤 센서가 이 판정에 얼마나 기여했는가"를 보여줄 수 있다는 게 SHAP의 핵심 가치입니다. 계수만으로는 "센서 A가 전체적으로 중요하다"까지만 말할 수 있지만, SHAP은 "이번 웨이퍼는 특히 센서 A와 B 때문에 불량으로 판단됐다"까지 설명할 수 있습니다.

## 4단계. 운영 환경을 가정해 재검증하기 (시간순 Walk-forward + 신뢰구간)

지금까지 보고한 성능(Recall 0.381)은 전체 데이터를 무작위로 섞어서 80%는 학습, 20%는 평가에 쓴 결과입니다. 그런데 1단계 EDA에서 **시간이 지날수록 불량률이 8.6%에서 4.7%로 떨어지는 추세**를 발견했었습니다. 무작위 분할은 이 흐름을 무시하고 과거·미래 데이터를 뒤섞어버리기 때문에, 실제 공정에 배치했을 때("과거 데이터로 학습해서 미래 웨이퍼를 예측")보다 성능이 낙관적으로 나왔을 가능성이 있습니다.

여기서 한 가지 더 짚을 게 있습니다 — 애초에 "Recall 0.381"이라는 숫자 자체도 테스트 샘플 314개(불량은 21건뿐) 위에서 나온 하나의 점 추정치입니다. **이 숫자가 얼마나 흔들릴 수 있는 값인지**부터 확인하지 않으면, 뒤에서 비교하는 다른 숫자들도 "진짜 차이"인지 "우연"인지 구분할 수 없습니다.

### 4-1. 지금까지의 숫자, 사실 신뢰구간이 꽤 넓었습니다

같은 테스트셋에서 무작위로 다시 뽑기(부트스트랩)를 2,000번 반복해서, "이 314개 테스트셋이 조금 달랐다면 Recall이 어느 범위에서 나왔을까"를 확인했습니다.

| 지표 | 점 추정치 | 95% 신뢰구간 |
|---|---|---|
| Recall | 0.381 | **0.167 ~ 0.588** |
| Precision | 0.098 | 0.037 ~ 0.165 |
| PR-AUC | 0.152 | 0.068 ~ 0.332 |

Recall 0.381이라는 숫자는 실제로는 **0.17에서 0.59 사이 어디든 나올 수 있는 값**이었습니다. 테스트 샘플이 314개(그중 불량은 21개)뿐이라 어쩔 수 없는 한계이며, 이후 다른 실험에서 "0.02~0.05 정도 개선됐다"는 식의 작은 차이는 이 신뢰구간 안에 다 들어가는, 사실상 노이즈와 구분하기 어려운 수준이라는 걸 먼저 인정하고 가야 합니다.

### 4-2. 단일 시간순 분할 — Recall 0은 우연이 아니었습니다

**무작위로 섞지 않고, 시간 순서 그대로 앞 80%(7월~10월 초)로 학습하고 뒤 20%(10월 초~중순)로 평가**했습니다. 이게 실제 공장에 모델을 배치했을 때와 가장 비슷한 상황입니다.

| 지표 | 무작위 분할 | 시간순 단일 분할 |
|---|---|---|
| Recall | 0.381 (부트스트랩 CI 0.167~0.588) | **0.000** |
| PR-AUC | 0.152 | 0.084 |

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/15_split_comparison.png" width="640" alt="무작위 분할 vs 시간순 분할 성능 비교">

시간순 분할의 Recall이 정확히 0(17건 중 0건 검출)이라 부트스트랩(고정된 예측 결과를 재표본추출)으로는 신뢰구간을 만들 수 없습니다. 대신 "실제 불량 17건 중 몇 건을 맞혔는가"를 이항 비율로 보고 **Clopper-Pearson 정확 신뢰구간**을 계산하면 **0% ~ 19.5%** 입니다. 즉 이 시기 테스트셋에서 모델이 낼 수 있었던 Recall의 상한이 매우 낮았다는 뜻입니다. 다만 무작위 분할과 시간순 분할은 애초에 서로 다른 테스트셋(불량 21건 vs 17건)이고 신뢰구간 계산 방식도 다르므로(부트스트랩 vs Clopper-Pearson), "구간이 겹치지 않는다"는 것 자체를 엄밀한 통계 검정으로 보기보다는, **무작위 분할보다 시간순 분할에서 현저히 낮은 성능이 관측됐으며 미래 구간 일반화가 어렵다는 증거**로 해석하는 것이 더 정확합니다.

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/14_chronological_confusion_matrix.png" width="380" alt="시간순 분할 혼동행렬">

### 4-3. Walk-forward — 언제부터, 어떻게 무너지는지 확인했습니다

단일 분할은 "8월~10월 초로 학습해서 10월을 맞혀봤더니 실패했다"는 딱 한 시점의 스냅샷입니다. **정말 전체 기간이 다 이런 건지, 특정 구간만 유독 어려운 건지**를 알아보려고, 학습 구간을 한 달씩 확장해가며(walk-forward) 그다음 구간을 예측하는 실험을 4번 반복했습니다.

| Fold | 평가 구간 | 실제 불량 수 | Recall | PR-AUC | No-skill 기준선 |
|---|---|---|---|---|---|
| 1 | 8/19 ~ 9/1 | 21건 | **0.619** (CI 0.384~0.819) | 0.055 | 0.067 |
| 2 | 9/1 ~ 9/20 | 11건 | 0.182 | 0.060 | 0.035 |
| 3 | 9/20 ~ 10/2 | 11건 | 0.000 | 0.036 | 0.035 |
| 4 | 10/2 ~ 10/17 | 17건 | 0.000 | 0.083 | 0.054 |

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/18_walk_forward_recall.png" width="640" alt="Walk-forward Recall 추이 (신뢰구간 포함)">

여기서 "No-skill 기준선"은 그 구간의 실제 불량 비율입니다 — PR-AUC가 이 값보다 낮으면, 모델이 매긴 확률 순위가 사실상 무작위로 순위를 매긴 것과 다르지 않다는 뜻입니다. **fold 1은 Recall만 보면 0.619로 가장 좋아 보이지만, PR-AUC(0.055)가 오히려 no-skill 기준선(0.067)보다 낮습니다.** 즉 이 구간에서 특정 임계값을 고정해두면 우연히 많이 걸러지긴 했지만(임계값을 낮게 걸어 많이 경보를 울린 효과에 가까움), 모델이 "어떤 웨이퍼가 더 위험한지" 순위를 매기는 능력 자체는 이 구간에서 딱히 없었다고 봐야 합니다. Recall 하나만으로 fold별 성능을 판단하면 오해할 수 있다는 걸 보여주는 사례입니다.

시간이 갈수록 Recall이 0.62 → 0.18 → 0.00 → 0.00으로 감소했습니다. 다만 fold 1의 PR-AUC가 이미 기준선 미달이었다는 점을 감안하면, "초반에는 잘 맞혔다가 점점 나빠졌다"고 단정하기보다 **이 시기 전반의 순위 판별력이 약한 상태에서 임계값 기준 Recall이 fold별로 크게 변동했다**고 해석하는 편이 타당합니다. 따라서 무작위 분할 성능만으로 배포 여부를 결정할 수 없고, 시간 구간별 성능 모니터링이 필요합니다.

### 정리

| 평가 방식 | Recall | 의미 |
|---|---|---|
| 무작위 분할 | 0.381 (CI 0.167~0.588) | 데이터 안에 배울 수 있는 패턴이 있는지 확인 |
| 시간순 단일 분할 | 0.000 (Clopper-Pearson 95% CI 0.000~0.195) | 해당 미래 구간에서 성능 저하가 관측됨 |
| Walk-forward 4 fold | 0.619 → 0.182 → 0.000 → 0.000 | 시간 구간별 변동이 커 드리프트 모니터링이 필요 |

처음 보고했던 Recall 0.381만으로는 미래 성능을 설명할 수 없었습니다. 실제 배포를 고려한다면 시간 구간별 Recall·PR-AUC를 모니터링하고, 성능 저하가 확인될 때 **재학습 또는 피처·임계값 재검토를 수행하는 절차**가 필요합니다.

### 4-4. 그런데 모델 선택은 무작위 분할 기준으로 정했었는데, 다시 봐도 맞을까요?

2단계에서 "Logistic Regression이 4개 모델 중 제일 좋다"고 정한 기준은 **무작위 분할** CV였습니다. 그런데 방금 무작위 분할이 실전을 못 대변한다는 걸 확인했으니, **모델을 고르는 기준 자체도 walk-forward로 다시 검증**하는 게 앞뒤가 맞습니다. 같은 4개 fold에서 4개 모델(Logistic Regression, Random Forest, XGBoost, SVM)을 전부 다시 비교했습니다.

| 모델 | 무작위 분할 CV Recall (기존) | Walk-forward 평균 Recall |
|---|---|---|
| **Logistic Regression** | **0.387** | **0.200** |
| SVM (RBF) | 0.120 | 0.012 |
| XGBoost | 0.072 | 0.036 |
| Random Forest | 0.036 | 0.000 |

<img src="https://raw.githubusercontent.com/ojineeee/SECOM_defect_prediction/main/results/figures/20_model_selection_walk_forward.png" width="640" alt="모델 선택: 무작위 분할 vs Walk-forward">

**다행히 순위가 그대로였습니다.** 두 평가 방식에서 절대적인 점수는 다르지만(walk-forward가 전반적으로 더 낮음), **어느 모델이 제일 나은가라는 순위는 동일하게 Logistic Regression이 1위**를 지켰습니다. 즉 "단순한 모델이 데이터 규모에 비해 낫다"는 원래 결론은 평가 방식을 더 엄격하게 바꿔도 흔들리지 않는, 견고한 결론이었다는 뜻입니다 — 모든 재검증이 항상 기존 결론을 뒤집는 건 아니고, 이렇게 "다시 확인해봐도 맞았다"는 것도 재검증의 정당한 결과입니다.

### 4-5. 운영 관점에서 다시 보기: Recall@상위 N%, 오경보 빈도, Precision@고정 Recall

Recall·Precision·PR-AUC는 모델을 비교하기엔 좋지만, 현장 담당자가 실제로 묻는 질문 — "이 모델을 켜두면 하루에 재검사를 몇 번이나 더 해야 하나", "불량의 절반을 잡으려면 오탐을 얼마나 감수해야 하나" — 에는 바로 답하지 못합니다. 이걸 확인하려고 무작위 분할 테스트셋(314건, 불량 21건) 위에서 세 가지를 추가로 계산했습니다.

> **읽는 법에 대한 주의**: 아래 수치, 특히 ②의 임계값은 별도의 validation set이 아니라 이 test set(`threshold_sweep.csv`) 위에서 탐색한 것입니다. 즉 "검증된 운영 임계값"이 아니라 **"이 test set에서는 이 정도 트레이드오프가 관찰됐다"는 탐색적 결과**로 읽어야 합니다. 실제로 운영에 쓸 임계값을 정하려면 별도 validation set에서 임계값을 고르고, test에서는 그 임계값 하나만 한 번 평가하는 구조가 필요합니다.

**① 위험도 상위 N%만 재검사한다면?**

모델이 매긴 불량 확률 순으로 정렬해서, 상위 N%만 재검사 대상으로 지정했을 때 실제 불량을 얼마나 잡는지입니다.

| 재검사 대상 | 검사 대상 수 | Recall | 웨이퍼 1,000장당 오경보 |
|---|---|---|---|
| 상위 5% | 16장 | 0.143 | 41.4건 |
| 상위 10% | 31장 | 0.190 | 86.0건 |
| 상위 20% | 63장 | 0.286 | 181.5건 |
| 상위 30% | 94장 | 0.429 | 270.7건 |

상위 30%를 재검사해도 실제 불량의 43%밖에 못 잡을 만큼, 이 모델의 순위 판별력 자체가 강하지 않다는 걸 다시 한번 보여주는 표이기도 합니다.

**② 목표 Recall을 먼저 정한다면, Precision은 얼마나 희생해야 하는가?**

| 목표 Recall | 실제 달성 Recall | 그때의 Precision | 임계값 |
|---|---|---|---|
| 0.3 | 0.333 | 0.100 | 0.55 |
| 0.5 | 0.619 | 0.078 | 0.25 |
| 0.7 | 0.714 | 0.081 | 0.20 |

Recall을 0.3대에서 0.7대로 두 배 이상 올려도 Precision은 0.08~0.10 사이에서 거의 바뀌지 않습니다 — 즉 이 모델로는 "더 많이 잡으려면 오탐도 그만큼 는다"가 아니라, **애초에 어느 임계값을 잡아도 Precision 자체가 낮은 구조**라는 뜻입니다. 이 표는 "재검사 비용과 불량 유출 비용을 비교해 임계값을 고른다"는 접근 자체가 어떻게 작동하는지 보여주는 탐색적 참고 자료이며, 위에서 밝혔듯 이 test set 위에서 찾은 값이라 실제 운영 임계값으로 그대로 확정하기 전에는 별도 validation set으로 다시 확인해야 합니다.

## 포트폴리오 핵심 역량

- **불균형 데이터를 다루는 경험**: 흔치 않은 사건(불량 6.6%)을 예측할 때 정확도가 아닌 올바른 평가 기준을 세우고, 이를 보정하는 방법을 비교·선택하는 과정
- **가설을 세우고 직접 검증하는 습관**: "시간이 지나며 불량이 준다"는 관찰을 파생변수로 만들어 실제로 성능이 개선되는지 교차검증으로 확인
- **여러 방법론을 공정하게 비교하는 절차**: 모델 4종과 이상탐지 2종을 비교하고, 이상탐지와 지도학습은 동일한 상위 5% 경고 예산으로 재평가
- **결과를 과장하지 않고 정직하게 해석하는 태도**: 성능 수치가 화려하지 않은 이유(데이터 자체의 낮은 신호 대 잡음비)와 한계를 숨기지 않고 기록
- **모델 해석(Explainability)**: SHAP으로 전역 중요도와 개별 사례 설명을 모두 확인하고, 계수 기반 중요도와 비교해 왜 두 방법의 결과가 다른지(상관관계 반영 여부)까지 설명
- **평가 방식 자체를 의심하고 재검증하는 습관**: 무작위 분할로 얻은 성능 수치를 그대로 믿지 않고, EDA에서 발견한 시간 드리프트를 근거로 "이 평가가 실전에서도 유효한가"를 시간순 분할과 walk-forward로 직접 재검증 — 그 결과 Recall이 시간이 지날수록 0.62→0.18→0.00→0.00으로 무너지는 패턴을 발견하고, 이걸 숨기지 않고 보고
- **성능 수치의 불확실성을 정량화하는 습관**: "Recall 0.381"처럼 하나의 숫자로만 말하지 않고, 부트스트랩 신뢰구간(0.167~0.588)까지 같이 제시 — 이후 실험에서 나온 개선폭이 노이즈 수준인지 실제 개선인지 판단할 수 있는 기준을 스스로 마련
- **의사결정의 근거를 끝까지 추적하는 습관**: "Logistic Regression이 최고"라는 결론이 신뢰할 수 없다고 밝혀진 무작위 분할 CV에서 나왔다는 걸 인지하고, 모델 선택 기준 자체를 walk-forward로 재검증 — 결론이 그대로 유지된다는 것까지 확인해 원래 선택의 근거를 더 단단하게 보강
- **점 추정치 하나로 판단하지 않는 습관**: 부트스트랩으로 신뢰구간을 못 만드는 경우(Recall이 정확히 0인 경우)에는 Clopper-Pearson 정확 이항 신뢰구간을 대신 쓰고, Recall만으로 fold별 성능을 판단하지 않고 PR-AUC를 no-skill 기준선(그 구간의 실제 불량 비율)과 비교해 "임계값이 우연히 잘 맞은 것"과 "순위 판별력이 실제로 있는 것"을 구분
- **비지도 파이프라인의 숨은 라벨 누수를 찾아 수정한 경험**: 정상 샘플만 남긴 뒤 상수 라벨로 피처를 선택하던 버그와 실제 불량률을 contamination에 사용하던 누수를 제거하고, 비교 조건을 다시 설계
- **학습·추론 피처 정의의 일관성 확보**: `days_since_start` 기준일을 train에서만 정하고 모든 validation/test 및 Walk-forward fold에 재사용하도록 구현
- **운영 관점에서 지표를 다시 번역하는 습관**: Recall·Precision 숫자를 "상위 N% 재검사 시 오경보/1,000장", "목표 Recall 달성 시 Precision" 같은 현장 의사결정에 바로 쓸 수 있는 형태로 다시 계산

## 한계점 (숨기지 않고 정리)

- 변수(센서)들이 익명화되어 있어 "이 센서가 왜 중요한지" 실제 공정 지식으로 설명하기는 어려웠습니다.
- 불량 사례가 원래 적어서(104건), 테스트셋이 작다 보니 성능 수치의 95% 신뢰구간이 상당히 넓습니다(Recall 0.17~0.59). 이후 실험 간 비교는 이 불확실성을 감안해서 해석해야 합니다.
- **4단계에서 확인했듯, walk-forward 검증에서 Recall이 시간이 지날수록 0.62→0.18→0.00→0.00으로 감소합니다.** 다만 fold 1은 PR-AUC 자체가 no-skill 기준선보다 낮아 "초반엔 잘 맞다가 나빠진다"기보다는 애초에 순위 판별력이 이 시기 전반적으로 약했을 가능성도 있습니다. 어느 쪽으로 해석해도 지금 상태로는 실전 배포에 바로 쓰기 어렵고, 최소한 주기적 재학습이나 드리프트 감지 장치 없이는 신뢰하기 어렵습니다.
- walk-forward의 초기 fold는 학습 표본이 작아(약 260~520개) 결측치가 많은 일부 센서의 대체값 신뢰도가 낮습니다.
- 이 프로젝트의 모든 성능 수치는 테스트셋 재표본추출(부트스트랩) 또는 이항 신뢰구간만 반영합니다. 랜덤 시드를 바꿔 재학습했을 때의 변동, 데이터 자체를 다시 수집했을 때의 변동까지는 정량화하지 않았습니다.
- One-class 이상탐지도 완전한 비지도 학습은 아닙니다 — 피처 선택 단계가 라벨을 쓰는 mutual information 기준이라 약한 지도 신호가 섞여 있습니다.
